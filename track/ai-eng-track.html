AI Engineering للـ Backend

من "يعني إيه LLM أصلًا؟" لحد ما تبني features حقيقية بالـ AI جوّه الـ backend بتاعك: بتتقاس، ومأمّنة، وعارف بتكلّف كام.

نوع الـ skill: technical (lab بأرقام حقيقية) + شوية judgment (إمتى تستخدم AI وإمتى لأ، وأنهي model، وبكام).

الإصدارات (اتأكدت منها يوم 2026-10-19 من الـ npm registry والـ docs الرسمية): @anthropic-ai/sdk 0.135.0 (اتنشر 2026-10-15) · الـ model الافتراضي claude-opus-5-5 · Node.js 26 + TypeScript 7.0.2 · zod 4.6.7 · pgvector 0.8.7 على Postgres 18 · MCP spec 2026-07-28 + @modelcontextprotocol/sdk 1.32.1 · Vercel AI SDK (ai) 7.0.143 للمقارنة في M16 · Ollama 0.40.6 + gemma4:e2b-it-qat عشان نجرّب ببلاش (اتضاف 2026-10-20). Ollama بيفهم الـ Anthropic Messages API، بس مبيدعمش prompt caching ولا Batches ولا citations ولا count_tokens، فالـ modules دي هتحتاج Claude نفسه. المراجع: SDK releases · Claude docs · MCP spec · pgvector.
اتغيّر في الإصدار الجديد (خلّي بالك من الـ tutorials القديمة) كتير من الشروحات على النت مكتوبة لـ models أقدم. في الـ models الحالية: temperature وbudget_tokens و"الـ prefill" (إنك تبدأ رد الموديل بنفسك) بقوا بيرجّعوا error. الـ JSON المنظّم بقى بـ output_config.format. والـ MCP في نسخة 2026-07-28 بقى stateless، يعني مفيش "handshake" في الأول. هنقف عند كل واحدة في الـ module بتاعها.
ليه TypeScript مش Python؟ Python هي اللغة الأشهر في الـ AI. بس شغلنا هنا backend بيكلّم models جاهزة، مش تدريب models. والـ SDKs بتاعة TypeScript فيها نفس الحاجات بالظبط. كمان ده نفس الـ stack اللي بتتعلّمه في تراك TypeScript / Node / NestJS، فالاتنين هيسندوا بعض. وM16 هيبني الكلام ده جوّه NestJS.

الحكاية في سطرين

الـ LLM زي موظف جديد ذكي جدًا، بس بيألّف لما ميعرفش، ومبيفتكرش حاجة من امبارح، وبياخد أجرته بالكلمة. شغلك كـ backend engineer إنك تديله المعلومة الصح، وتراجع شغله بالأرقام، وتمنعه يعمل مصيبة، وتحسب تمنه.

الفكرة 1

الكيبورد بتاع موبايلك، بس عملاق

لما بتكتب على الموبايل "أنا رايح"، الكيبورد بيقترح 3 كلمات: "البيت"، "الشغل"، "النادي". هو مش فاهم إنت رايح فين. هو بس شاف الكلام ده كتير قبل كده، فبيخمّن الكلمة اللي غالبًا جاية.

دلوقتي تخيّل كيبورد اتعلّم من كمية نصوص مهولة. ولما يختار كلمة، يحطّها ويخمّن اللي بعدها، وهكذا لحد ما يكتب فقرة كاملة.

الكيبورد العملاق ده اسمه LLM (Large Language Model). Claude وChatGPT وGemini كلهم كده.

اتأكد إنك فهمت: الـ LLM في كل خطوة بيعمل إيه بالظبط؟
الإجابةبيخمّن الحتة اللي غالبًا جاية بعد الكلام اللي قدّامه، ويضيفها، ويكرّر. هو مش بيدوّر على "الإجابة الصح" في مكان. هو بيكمّل الكلام بالشكل اللي شافه كتير.
الفكرة 2

مش بيقرا كلمات، بيقرا حتت

الـ LLM مش بيشوف الكلمة كاملة. بيقطّعها حتت صغيرة، زي ما بتقطّع ساندويتش طويل عشان يدخل بُقّك. كلمة سهلة ومشهورة ممكن تبقى حتة واحدة. وكلمة طويلة أو نادرة بتبقى كذا حتة.

الحتة دي اسمها token.

قاعدة تقريبية: في الإنجليزي كل token حوالي 4 حروف. والعربي غالبًا بياخد tokens أكتر لنفس المعنى. هتعرف ليه ده مهم في الفكرة 4.

اتأكد إنك فهمت: جملة فيها 10 كلمات إنجليزي، هتبقى بالظبط 10 tokens؟
الإجابةمش شرط. ممكن تبقى أكتر، لأن الكلمات الطويلة أو النادرة بتتقطّع كذا token. والعلامات زي النقطة والفصلة بتتحسب tokens كمان.
الفكرة 3

الـ backend بيكلّمه زي أي API

الـ LLM مش بيشتغل جوّه السيرفر بتاعك. هو قاعد عند الشركة اللي عملته، والـ backend بتاعك بيبعتله request على الإنترنت، زي ما بتكلّم أي API تاني (Stripe أو Firebase مثلًا). بتبعت السؤال، وبيرجعلك الرد ومعاه عدد الـ tokens.

الشركة الواحدة عندها كذا "مخ"، فيه الكبير الشاطر الغالي، وفيه الصغير السريع الرخيص. وإنت بتقول في كل request عايز أنهي واحد.

الـ "مخ" اللي بتختاره ده اسمه model، زي claude-opus-5-5.

وده شكله بالكود، بالـ SDK الرسمي في TypeScript:

import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic();
const res = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 1000,
  messages: [{ role: "user", content: "What is a refund?" }],
});

بص على حاجتين بس: model هو المخ اللي اخترته، وmessages هو الكلام اللي بتبعته. وmax_tokens هو أقصى طول للرد.

الكود ده اتعمله type-check على @anthropic-ai/sdk 0.135.0 ووصل للـ API فعلًا. هيشتغل عندك كامل أول ما تحط الـ API key في Task 2.

من Laravelنفس فكرة Http::post('https://api.stripe.com/...', [...]). الفرق إن الـ SDK بيلفّ الـ HTTP ده في function جاهزة، وبيعمل retry لوحده لو النت قطع.
اتأكد إنك فهمت: لو غيّرت model من الكبير للصغير، إيه اللي هيتغيّر وإيه اللي هيفضل زي ما هو؟
الإجابةالكود نفسه هيفضل زي ما هو، كلمة واحدة بس اتغيّرت. اللي هيتغيّر هو جودة الرد وسرعته وتمنه. واختيار الـ model ده قرار هنتعلّم ناخده بالأرقام في M10.
الفكرة 4

بتدفع بالعدّاد

تخيّل تاكسي بعدّاد غريب: بتدفع على كل كلمة إنت بتقولها للسوّاق، وبتدفع أكتر بكتير على كل كلمة هو بيردّ بيها.

الـ tokens اللي إنت بتبعتها اسمها input tokens، واللي الموديل بيكتبها اسمها output tokens. وكل نوع ليه سعر.

الأسعار دي من جدول الأسعار الرسمي (أكتوبر 2026). شوف إن الـ output أغلى 5 مرات من الـ input.

حسبة سؤال واحد قصير على Opus: 20 token رايحين و200 راجعين.

رقم صغير؟ لو عندك 100,000 سؤال في اليوم، يبقى حوالي $408 في اليوم. عشان كده الـ backend engineer لازم يعرف يحسبها.

اتأكد إنك فهمت: عندك طريقتين لنفس الـ feature: الأولى بتبعت 1000 token وبترجّع 50، والتانية بتبعت 100 وبترجّع 500. أنهي أرخص على Opus؟
الإجابةالأولى: 1000×4 + 50×20 = 5,000 وحدة. التانية: 100×4 + 500×20 = 10,400 وحدة. يعني الأولى أرخص بحوالي النص، مع إنها بتبعت كلام أكتر بـ 10 مرات. السبب إن الـ output أغلى بكتير.
الفكرة 5

كل مرة بيخمّن من الأول

الـ function العادية في الكود بتاعك: نفس الـ input، يبقى نفس الـ output، كل مرة. الـ LLM مش كده. هو بيرمي "زهر" وهو بيختار الكلمة الجاية، فنفس السؤال ممكن ياخد إجابة مختلفة كل مرة.

والأخطر: لما يركّب حتت شافها قبل كده، ممكن يطلع بجملة شكلها مظبوط جدًا، بس هي غلط. هو مش "بيكدب". هو بس بيكمّل الكلام بالشكل المعتاد.

الإجابة الغلط اللي بتطلع بثقة دي اسمها hallucination.

اتأكد إنك فهمت: لو سألت الـ LLM نفس السؤال مرة وطلعت الإجابة صح، ينفع تقول إن الـ feature شغّالة؟
الإجابةلأ. مرة واحدة صح ممكن تكون حظ. لازم تجرّب على حالات كتير وتعدّ كام مرة صح. والطريقة دي اسمها evals، وهنبنيها في M8.

الفكرة 1

كارت التعليمات قبل ما الزباين تيجي

تخيّل موظف خدمة عملاء جديد. قبل ما يقعد على المكتب، المدير بيدّيله كارت: "إنت بتشتغل في محل هدوم. اتكلّم بأدب. جاوب في سطر واحد. متوعدش حد بخصم".

الزبون عمره ما بيشوف الكارت ده. بس الموظف بيمشي عليه في كل رد.

الكارت ده اسمه system prompt. ده التعليمات الثابتة اللي الـ backend بتاعك بيبعتها للموديل، بعيد عن كلام الزبون.

await client.messages.create({
  model,
  max_tokens: 1000,
  system: "You are a support agent for an online shop. Answer in one short sentence.",
  messages: [{ role: "user", content: "How long does a refund take?" }],
});

الجديد هنا سطر واحد بس: system.

اتأكد إنك فهمت: عايز الـ bot يرد بالعربي دايمًا مهما الزبون كتب بأي لغة. تحط الكلام ده فين؟
الإجابةفي الـ system prompt، عشان دي قاعدة ثابتة لكل المحادثات، مش حاجة الزبون بيقولها.

الـ API محتاج نفس الحكاية. كل رسالة في messages لازم يتقال مين صاحبها: الزبون، ولا الموديل.

صاحب الرسالة اسمه role. رسايل الزبون "user"، وردود الموديل "assistant".

messages: [

  { role: "user", content: "Where is it now?" },
]
اتأكد إنك فهمت: آخر رسالة في messages قبل ما تبعت الـ request، غالبًا بتبقى role إيه؟
الإجابة"user". إنت بتبعت عشان الزبون سأل حاجة جديدة، والموديل هو اللي هيرد عليها.
الفكرة 3

كاشير بيقابلك كأنها أول مرة، كل مرة

تخيّل كاشير ذاكرته بتتمسح كل ما تمشي من قدّامه. قلتله اسمك، ومشيت خطوة، ورجعت سألته "أنا مين؟". هيقولك "معرفش".

الحل الوحيد: كل مرة تروحله، تدّيله ورقة مكتوب فيها كل اللي اتقال قبل كده.

الـ API ده بالظبط كده. مبيفتكرش أي حاجة بين request والتاني. وده اسمه stateless.

من LaravelHTTP نفسه stateless، وLaravel بيعمل الـ session ويشيلها لك في الـ cookies أو Redis. هنا مفيش حد بيعمل كده لوحده. إنت اللي بتخزّن المحادثة (في الـ database أو Redis)، وإنت اللي بتبعتها كلها مع كل سؤال.
اتأكد إنك فهمت: ChatGPT بيفتكر كلامك من 10 رسايل فاتوا. مين اللي فاكر فعلًا، الموديل ولا حاجة تانية؟
الإجابةالـ backend بتاع ChatGPT. هو بيخزّن المحادثة، وبيبعتها كلها للموديل مع كل رسالة جديدة. الموديل نفسه مبيفتكرش حاجة.
الفكرة 4

الورقة بتطوّل، والعدّاد بيزيد

افتكر عدّاد التاكسي من M1: بتدفع على كل كلمة بتقولها. ودلوقتي إنت بتعيد المحادثة كلها مع كل سؤال.

يعني أول رسالة بتبعت سطر. والعاشرة بتبعت 10 أسئلة و9 ردود. والـ system prompt كمان بيتبعت مع كل واحدة.

كل رسالة جديدة أغلى من اللي قبلها، حتى لو السؤال نفسه قصير.

ولو جمعت الـ 10: 100 + 200 + ... + 1000 = 5,500 input token. ولو كل رسالة كانت لوحدها كان المجموع 1,000 بس. يعني دفعت 5.5 مرات أكتر علشان الموديل "يفتكر".

اتأكد إنك فهمت: نفس المثال، بس المحادثة 20 رسالة. مجموع الـ input tokens كام تقريبًا؟
الإجابة100 × (1 + 2 + ... + 20) = 100 × 210 = 21,000. المحادثة طولها اتضاعف، بس التكلفة زادت حوالي 4 مرات. عشان كده المحادثات الطويلة غالية.
الفكرة 5

السبورة ليها مساحة

تخيّل إن الورقة اللي بتدّيها للموديل مكتوبة على سبورة. السبورة ليها مساحة محدودة. لما تتملي، لازم تمسح حاجة.

جواب مكتوب، ولا فورمة متعبّية؟

تخيّل موظف بيستقبل شكاوى، ومطلوب منه يسجّل كل شكوى في السيستم. لو كتبلك جواب: "الزبون ده شكله متضايق جدًا بخصوص الشحنة 4417"، إنت لازم تقرا الجواب وتطلّع منه المعلومة بإيدك.

بس لو ملالك فورمة فيها خانات (النوع: شحن، الأولوية: عالية، رقم الطلب: 4417)، الكود بتاعك يقدر يقرا كل خانة لوحدها على طول.

الرد اللي جاي في خانات ثابتة، الكود يقدر يقراه، اسمه structured output. وفي الـ backend الفورمة دي غالبًا بتبقى JSON.

const data = JSON.parse(text);   // text = رد الموديل
await db.tickets.insert({ category: data.category, urgency: data.urgency });
اتأكد إنك فهمت: عايز تعمل route بيوزّع كل شكوى على القسم الصح (billing أو shipping أو technical). محتاج من الموديل إيه؟
  1. أ) رد مكتوب بأدب للزبون
  2. ب) JSON فيه خانة category قيمتها واحدة من الأقسام دي
  3. ج) ملخّص للشكوى في 3 سطور
  4. د) الموديل نفسه يبعت الشكوى للقسم
الإجابةب. الكود بتاعك هو اللي هيعمل if (data.category === "billing")، فمحتاج خانة ثابتة بقيمة معروفة. (أ) و(ج) نص حر، الكود مايقدرش يعمل عليه if. و(د) الموديل مابيبعتش حاجة لحد، هو بيرجّع نص بس (إلا لو إديته tool، ودي M5).
الفكرة 2

طلبت JSON، جالك JSON في ظرف

أسهل حاجة: تكتب في الـ prompt "رد بـ JSON بس". والموديل غالبًا هيكتب JSON سليم فعلًا.

بس هو متعوّد يكتب للبني آدمين. فساعات بيحط الـ JSON جوّه "ظرف": ```json قبله و``` بعده، زي ما بيحصل في الشات. أو يكتب "Sure! Here it is:" الأول.

الظرف ده اسمه code fence. والبني آدم مش بيشوفه أصلًا، بس JSON.parse بيقع منه على طول.

JSON.parse('{"a": 1}');               // ✓ { a: 1 }
JSON.parse('```json\n{"a": 1}\n```');  // 💥 SyntaxError: Unexpected token '`'
اتأكد إنك فهمت: الرد كان "Sure! {\"urgency\": \"high\"}". JSON.parse هيعمل إيه؟
  1. أ) هيرجّع { urgency: "high" } ويتجاهل الكلام اللي قبله
  2. ب) هيرجّع الـ string زي ما هو
  3. ج) هيرمي SyntaxError
  4. د) هيرجّع null
الإجابةج. JSON.parse مش بيدوّر على JSON جوّه الكلام. لازم النص كله من أوله لآخره يكون JSON، غير كده بيرمي error. وده اللي بيخلّي (أ) غلط رغم إنها منطقية لبني آدم.
الفكرة 3

بوّاب على الباب: JSON سليم مش كفاية

افرض شِلت الظرف، وJSON.parse نجح. لسه ممكن يجيلك "category": "Damaged Item"، وده مش من الأقسام بتاعتك. أو "urgency": "High" بـ H كابيتال. أو orderId: 4417 رقم بدل string.

كل دول JSON سليم 100%، بس الكود بتاعك هيمشي غلط بيهم من غير ما يقع، وده أوحش.

الحل: بوّاب بيقارن كل رد بوصف ثابت للشكل المطلوب. الوصف ده اسمه schema، والمكتبة اللي هنستخدمها للبوّاب اسمها zod.

import { z } from "zod";

const Ticket = z.object({
  category: z.enum(["billing", "shipping", "technical", "other"]),
  urgency: z.enum(["low", "medium", "high"]),
  orderId: z.string().nullable(),
});

const result = Ticket.safeParse(data);
if (result.success) save(result.data);      // result.data متأكدين من شكلها
else console.log(result.error.issues);      // إيه اللي غلط بالظبط
من Laravelده زي $request->validate(['category' => 'required|in:billing,shipping,technical,other']) بالظبط. الفرق إن الـ input هنا جاي من الموديل مش من الزبون. وبرضه مش بتثق فيه.
اتأكد إنك فهمت: الموديل رجّع {"category": "billing", "urgency": "urgent", "orderId": null}. Ticket.safeParse هيرجّع إيه؟
  1. أ) success: true، عشان الـ JSON سليم
  2. ب) success: false، عشان orderId بـ null
  3. ج) success: false، عشان "urgent" مش من low / medium / high
  4. د) هيرمي SyntaxError
الإجابةج. الـ enum بيقبل الـ 3 قيم دول بس. (ب) غلط عشان إحنا كاتبين .nullable()، يعني null مسموح. و(د) غلط عشان zod مش بيعمل parse لنص، ده بيتحقّق من object طالع من JSON.parse خلاص.

يعني تبعت للموديل تاني نفس المحادثة، وتضيف عليها رده الغلط، ورسالة فيها الـ error اللي zod قاله بالظبط.

ده اسمه retry with feedback. وبتحط له حد (مثلًا محاولتين زيادة بس)، عشان كل محاولة بتتحسب tokens، فاكر عدّاد التاكسي؟

messages.push({ role: "assistant", content: text });
messages.push({ role: "user", content: `Your JSON was invalid: ${issues}. Reply with corrected JSON only.` });
// وتبعت تاني، بحد أقصى محاولتين زيادة
اتأكد إنك فهمت: في 50 شكوى، 45 عدّوا من أول مرة، و5 محتاجين محاولة تانية. المحاولة التانية بتبعت إيه بالظبط؟
  1. أ) رسالة الـ error بس، عشان الموديل فاكر الشكوى
  2. ب) الشكوى + رد الموديل الغلط + رسالة الـ error
  3. ج) نفس الـ request الأولى بالظبط، يمكن المرة دي يطلع صح
  4. د) الشكوى بس، من غير الرد الغلط، عشان نوفّر tokens
الإجابةب. الموديل stateless (M2). لو بعت الـ error بس (أ)، مش هيعرف بتتكلم عن إيه. و(ج) ممكن تنفع ساعات عشان الموديل مش بيرد نفس الرد كل مرة (M1)، بس إنت بترمي المعلومة المهمة: هو غلط فين. و(د) نفس المشكلة.

استمارة بخانات مقفولة: الغلط مايتكتبش أصلًا

كل اللي فات بيصلّح الغلط بعد ما يحصل. فيه طريقة أحسن: استمارة أونلاين خانة "الأولوية" فيها dropdown بـ 3 اختيارات بس. مستحيل تكتب فيها "urgent".

الـ Claude API فيه نفس الحكاية: تدّيله الـ schema، وهو بيكتب الرد كلمة كلمة، مش بيسمح لأي token يخالف الـ schema يطلع أصلًا. ودي نفس الـ feature اللي في حكاية أول الـ module.

ده اسمه constrained decoding. وفي الـ SDK بتستخدمه بـ output_config.format، والأسهل client.messages.parse مع zod.

import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod";

const res = await client.messages.parse({
  model, max_tokens: 1000,
  messages: [{ role: "user", content: ticket }],
  output_config: { format: zodOutputFormat(Ticket) },
});
res.parsed_output;   // { category, urgency, orderId } متحقّق منه
جرّبناها على Ollama: الـ Anthropic endpoint بتاع Ollama 0.40.6 بيتجاهل output_config.format. الموديل كتب "This support ticket..." نص عادي، وmessages.parse وقع بـ Failed to parse structured output as JSON. عشان كده الـ lab هيستخدم الأفكار 2 و3 و4 (تشيل الظرف، وzod، والـ retry). ولو شغّال على Claude، الفكرة 5 هي اللي تستخدمها في الـ production.
اتأكد إنك فهمت: شغّال على Claude بـ output_config.format. لسه محتاج zod يتحقّق من الرد في الكود؟
  1. أ) لأ خالص، الـ API ضامن الشكل 100% في كل الحالات
  2. ب) أيوه، عشان لو الرد اتقطع بسبب max_tokens أو الموديل رفض يرد، الـ JSON ممكن يبقى ناقص
  3. ج) أيوه، عشان constrained decoding مش بيشتغل غير مع الـ enums
  4. د) لأ، بس لازم تعمل retry 3 مرات على كل request
الإجابةب. الـ schema بيتحكّم في كل token بيطلع، بس مايقدرش يكمّل رد اتقطع (stop_reason: "max_tokens"، فاكر Task 4 في M1؟) أو رد الموديل رفض يكمّله ("refusal"). وكمان zod بيدّيك type في TypeScript. (ج) غلط، هو بيشتغل مع objects وstrings وأرقام كمان. وده هنكمّله في M4.

غلطات مشهورة

  • تعمل JSON.parse(text) على الرد على طول من غير try، فأول code fence يوقّع الـ server.
  • تتحقّق إن الـ JSON سليم بس، ومن غير ما تتأكد من القيم، فـ "High" و"Damaged Item" يدخلوا الـ database.
  • تعمل retry من غير حد، فرد واحد غلط يفضل يلف ويدفّعك.
  • تفتكر إن output_config.format شغّال على أي provider. اتأكد الأول (Ollama بيتجاهله).
